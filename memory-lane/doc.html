DEFINITION一文定義

MEMORY LANEは、未来の自分が見たくなる瞬間に、今の自分が気づくためのサービス。

撮った写真を整理するのではなく、
撮らなかったはずの瞬間を生み出す。
一人では残らなかった日常を、その場にいたみんなの視点で残し、
一つのMemoryとして未来へ届ける。
3つの「〜ではない」
  • 写真共有アプリではない（集める場所の勝負をしない）
  • 写真整理アプリではない（撮った後の整頓をしない）
  • AI動画生成アプリではない（生成の綺麗さで勝たない）

介入するのは、シャッターを押した「後」ではなく、押す「少し前」。既存サービスが取れていないのはここだけ。

01解決したいこと

人は「撮りたい」と思ったものしか撮らない。しかし未来に見たくなるのは、必ずしも「撮ろうと思った瞬間」だけではない。

  • 友達が爆笑していた瞬間 ／ 彼女が海を見ていた横顔
  • ホテルでくだらない話をしていた夜 ／ ドライブ中の車内
  • 部活終わりの部室 ／ 子どもを見ながら笑っていた母親

その時は「写真に残すほどじゃない」と思っていた時間が、5年後10年後には最も見たい時間になる。価値に気づいた時には、もう撮れない。MEMORY LANEはこの後悔を減らす。

02Natural Memory

「写真撮るよ！」と言った瞬間、人はカメラを見て、姿勢を直して、表情を作る。撮ろうとしたことで、本当に残したかった自然な瞬間が消える。

だからMEMORY LANEは、撮られる人ではなく、撮る人にきっかけを与える。参加者はMemoryへの参加に同意している。ただし「次の写真がいつ撮られるか」までは意識していない。だから自然な表情が残る。

絶対に守る線

隠し撮りを目的としたサービスにはしない。同意・公開範囲・削除権限は、後付けの機能ではなく最初からプロダクト設計に入れる。参加していない人はMemoryに入らない。自分が写ったものは、理由を書かずにいつでも消せる。ここを緩めた瞬間に、これは別のサービスになる。

各画面で決めておくべきこと

画面設計上の判断
01 QRネイティブアプリのインストールを参加の条件にしない。Web（PWA）でMemoryに参加でき、Movieの受け取り時にだけメール／SNS／アプリを選ばせる。ここを間違えると参加率が半分以下になる。
02 参加同意画面をスキップ不可・全文表示。ただし文言は4行まで。長い規約は読まれず、読まれない同意は同意ではない。
03 名前アカウント作成は「Movieが届く直前」まで遅らせる。旅の初日に登録を求めない。
04 Missionプッシュ通知は1日1回まで。時刻指定をしない代わりに、その日の行動が始まる時間帯（朝）に1回だけ置く。
05 撮影アプリ内カメラで撮る／端末カメラロールから選ぶ、両方を許可する。「アプリで撮らないとMissionにならない」は体験を壊す。
06 共有誰が撮ったかは表示するが、「誰が何枚撮ったか」のランキングは出さない。競争にした瞬間に自然さが消える。
07-08 投票対象者本人の端末にだけ別Missionを配る。本人に「あなたが撮られています」と絶対に通知しない。
10 生成待たせる。即完成はSNS的な消費になる。「後日届く」という体験がこのサービスの記憶装置。
11 到着視聴画面の直下にひとことスペース。「これいつ撮った？」が出るかどうかがMVPの合否判定そのもの。

サブフロー

  • 途中参加：2日目に合流した人も、同じQRから参加。その人には合流日からのMissionが配られる。
  • 削除依頼：ギャラリーの各写真から「自分が写っている／消したい」→ 即時非表示、AI編集からも除外。
  • 未参加者の写り込み：写り込んだだけの人は識別対象にしない（顔認識で個人を特定して結び付けない）。
  • Movie再編集：気に入らないシーンを1つだけ差し替えられる。全編集はさせない（作品性を保つため）。

②Missionの具体例 50個

Missionは「◯時に写真を撮ってください」ではない。撮影を義務にしない。撮る人の頭の中に視点だけを置く。データ実体は missions.js（app.html / biz.html と共有）。

Missionを書くときのルール

ルール理由
時刻を指定しない指定した瞬間に「作業」になる。撮る側の生活のリズムを壊さない。
ポーズを指定しないポーズを作らせた時点でNatural Memoryではない。
被写体は指定しても、撮り方は指定しない「ユウキを撮ろう」まではいい。「笑顔のユウキを正面から」はダメ。
1文で言い切る頭の片隅に置いておける長さでないと、一日持たない。
失敗できる余地を残す撮らない日があっていい。達成率を上げにいくと、写真がつまらなくなる。
誰も傷つけない「一番太った人」「一番ダサい人」系は永久に不採用。笑いの方向を必ず内側に向ける。

Missionの配り方（アルゴリズムの初版）

  1. Memory作成時に シーン（旅／BAR／学校…）と 人数と 日数を取得。
  2. DAY1は全員に T01「まず、全員が写った一枚を」を固定配布（起動儀式）。
  3. DAY1夜に「一番撮っている人は？」投票。過半数の人物を 撮られ役に設定。
  4. DAY2は撮られ役以外の全員に T02、撮られ役本人には別Mission。
  5. DAY3以降は、参加者ごとに被らないようにrole（other／group／place）を分散して配布。
  6. 最終日は全員に T12「何でもない今を一枚」を固定配布（着地）。
  7. 店舗・施設が設定したMissionは、その場所のQRを読んだ人にだけ、当日限りで割り込む。

③MVPで必要な機能一覧

MVPで証明することは、たった一つ

「このサービスがあったから、本来なら存在しなかった写真・動画が生まれたか？」

YESなら進む。NOなら、どれだけAI動画が綺麗でも失敗。ポイントも地図も行政連携もホテル管理画面も10年後通知も、この判定の後でいい。

機能MVP内容
QR発行・読み取り必須Memory単位・設置場所単位でURL発行。読み取り＝参加導線。運営が手動発行でも可。
Memory作成必須名前・期間・人数（2〜6人）・シーン。作成は主催者、またはQRを置いた店舗。
参加・同意必須同意表示、ニックネーム、参加者一覧。ログインなし（端末トークン）で開始できる。
Mission配信必須1日1〜2件、参加者ごとに別。プッシュまたはLINE/メール通知。手動配信でも初回は可。
撮影・アップロード必須写真・動画・音声。カメラロール選択も可。撮影時にMission IDを紐づける。
共有ギャラリー必須参加者全員の投稿を時系列表示。撮影者表示。削除は本人と被写体本人が可能。
「いつも撮る人」投票必須このサービスの独自性の核。ここを削るとただの共有アルバムになる。
Memory Movie生成必須3〜5分。初期は半自動（AIが素材選定＋人が最終確認）で構わない。品質のほうが自動化より重要。
完成通知・視聴必須参加者全員に配信。視聴画面にひとことスペース。
ひとこと（反応）必須「これいつ撮った？」が出るかを計測するための最小チャット。
元データDL推奨参加者が自分の写真を持ち帰れる。「囲い込まない」姿勢の証明になる。
1週間後の再通知推奨実装が軽い割に、リテンション検証の価値が高い。1年後以降はVer.2で可。
店舗Mission差し込み推奨BtoB検証を並走するなら必要。運営が手で登録する形でよい。
ポイント・特典後回しゲーム設計は体験が固まってから。
Memory Map後回し位置情報の同意設計が重い。MVPに入れない。
BtoB管理画面後回し最初の10店舗は運営が代行設定すれば足りる。
行政・DMO連携後回し数字が出てから。
1年後〜10年後通知後回しデータ保持方針とセットで設計する必要がある。
顔認識による人物紐付け要検討体験上は強力だが、同意設計とプライバシー負荷が跳ね上がる。MVPでは入れない。

MVPの規模感

  • 対象：2〜6人・1つのMemory・最長7日。それ以上は当面受け付けない。
  • プラットフォーム：Web（PWA）優先。ネイティブはMovie受け取りとカメラ品質が問題になってから。
  • 最初の検証：沖縄の BAR・ホテル 各1〜3施設＋知り合いの旅行グループ10組。
  • 「AIで完全自動編集」はMVPの要件から外す。人手で編集しても、判定したい問いには答えが出る。

BtoBの提供価値の定義

お店は広告枠を買うのではなく、Memoryの箱を置く。ユーザーにとってはMemory、ホテルにとっては「広告ではなく思い出の中にホテルが入る」。そのMovieは後日、宿泊者自身の手でInstagramやTikTokに出ていく。店が一方的に発信するのではなく、客が自分の思い出として発信する。ここがBtoB価値。

  • 写真そのものを売らない・使わない。広告学習データとしての二次利用もしない。

  • 閲覧回数を伸ばす設計にしない。滞在時間を伸ばすほど、思い出の価値は下がる。

領域案

ストレージオブジェクトストレージ＋署名付きURL。原本は保持、配信は変換後。保存期間の方針を先に決める（未決定）。
Mission配信初期はルールベースで十分。LLMは「店舗が作ったMission文の審査」と「Movieの字幕・構成案」に使う。
Movie生成素材選定（スコアリング）→構成→レンダリング。初期は人が最終確認する半自動。レンダリングはFFmpegベースのテンプレート合成から始め、生成AIの映像は使わない（実在の記憶に嘘を混ぜない）。
通知Web Push＋メール。日本の実運用ではLINEも現実的な選択肢。

07AI編集の中身（何を評価して選ぶか）

AIに写真を撮らせる必要はない。人間が「瞬間」を見つけ、AIが「思い出」を編集する。役割を分ける。

素材スコアリングの軸（初版）

  • Naturalness：カメラ目線がない／ポーズがない／撮影者以外が撮影を意識していない
  • Mission適合：どのMissionに紐づいて撮られたか（撮影意図が既知であることが強み）
  • 視点の多様性：同じ被写体を、何人の視点から撮っているか
  • 登場バランス：写っている回数が少ない人を優先的に拾う（＝撮る人が消えないため）
  • 音：笑い声・話し声・環境音のある区間を優先
  • 時間の連続性：名所より、移動・待ち時間・部屋の中を意図的に混ぜる

編集で避けること

  • ハイライトだけを並べない。旅の8割は「何でもない時間」で、そこがこのサービスの主戦場。
  • 生成AIで映像を作らない・盛らない。無かった景色を足した瞬間に、記録としての信頼が消える。
  • BGMを主役にしない。現地の音を残す区間を必ず入れる。

09リスクと法務・倫理

論点対応方針
隠し撮りへの転用参加者以外はMemoryに入らない。参加時に必ず同意。通知なしで撮られる範囲は「同意済みの参加者同士・そのMemoryの期間中のみ」に限定。第三者が写り込んだ素材は、本人特定処理を行わない。
肖像権・削除権被写体本人からの削除依頼を、撮影者の同意なしで即時実行。AI編集後のMovieからも再生成で除去。
未成年学校・部活での利用は保護者同意フローを必須化。同意のない生徒はMemoryに入れない。
個人情報顔認識による人物データベース化はMVPで実装しない。位置情報はMemory単位の粗い粒度に丸める。
データ保持「10年後に届く」を謳う以上、保管年数・退会時の扱い・サービス終了時のエクスポートを最初に明記する。ここを曖昧にしたまま10年後通知を売り文句にしない。
店舗への提供範囲画像そのものは渡さない。集計値のみ。個別画像は本人が個別に許可したときだけ。
悲しみの商品化死別・別れを訴求コピーに使わない。失ってから残すのではなく、何でもない今のうちから残す。この一線を、マーケティング側にも共有する。

10開発ステップ

この構想の一番弱い部分は技術ではなく、「Missionを渡された人が、本当にいつもと違う写真を撮るのか」という仮説。ここはアプリがなくても検証できる。作る前に3組でやったほうがいい。

11未決定の論点（次に決めるべきこと）

  1. Memoryの単位：旅行1回か、店舗1回の来店か。両方だとMovieの粒度が壊れる。おそらく「旅行＝親Memory／店舗＝子Memory」の入れ子。
  2. 誰がMemoryを作るか：ユーザー（幹事）か、店舗か。BtoBから入ると店舗が作る形になるが、旅全体を包むMemoryは幹事しか作れない。
  3. Movieの尺と納品時間：3分か5分か、翌日か1週間後か。待たせるほど体験は強くなるが、離脱もする。
  4. 価格：¥1,800は根拠のない置き数字。P1で「いくらなら払うか」を必ず聞く。
  5. 保存年数の約束：10年後通知を機能として謳うなら、事業継続とセットでの約束になる。
  6. アプリかWebか：参加率（Web有利）と撮影体験・通知（アプリ有利）のどちらを優先するか。
