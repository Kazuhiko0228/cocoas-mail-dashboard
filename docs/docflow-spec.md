# 監査書類の自動作成（docflow）— 実装指示 v1.0

> 対象：Miralink「提出書類ナビ」の各書類行に、**Import → 解析 → 自動入力 → 質問 → 回答 → 二重チェック → 確定・原本レイアウトで出力** を載せる。
> 元の大枠：安田さんの「監査書類自動作成フロー 仕様書 v0.1」（2026-09-23）。
> この文書は、その大枠に **2026-09-24 の合意5点** と **既存コードの制約** を足した、実装のための指示書です。
>
> 読む人：画面側（`cocoas-dashboard`）＝ Claude Code、サーバ側（`cocoas-api`）＝ 担当チーム。
> 両リポジトリの `CLAUDE.md` / `AGENTS.md` の決めごと（ES5・`★`・`tenant_id`・`wrap()` など）は、ここでも全部守ります。

## 0. 動かさない線（ここを崩す実装は差し戻し）

| # | 線 | なぜ |
|---|---|---|
| 1 | **自動でやるのは ②解析・③自動入力・④質問生成まで。⑤回答は園、⑥⑦は人間の承認** | AIが解析結果をそのまま確定させる事故を、構造で起こせなくする |
| 2 | **A/B/C の判定に迷ったら C** | A/B と誤判定して、システムが勝手に埋めるのが最悪の事故 |
| 3 | **園児・職員の実データは AI に一切送らない** | ②で送るのは「様式」と「Miralink の項目名の目録（中身は空）」だけ。③の値入れと B の計算はサーバの中だけで行う |
| 4 | **B の計算は AI にさせない** | 常勤換算・配置基準は、サーバのコードに関数として固定で持つ。桁の誤りに気づけないため |
| 5 | **確認済みになるのは、全項目に「確認しました」が入ったときだけ** | A/B の自動入力にも根拠を出し、確認を省略させない |
| 6 | **確定したものは上書きしない。直すときは新しい版** | 監査で「いつ誰が何を確定したか」を出せるように |
| 7 | **採寸（様式のどこに何を書くか）が済んでいない様式は、原本レイアウトで出力しない** | ずれたまま出力するのが、見た目の最悪の事故 |
| 8 | **園ごとにデータを閉じる** | 他園との共有・横断レコメンドは今回やらない |

## 1. 合意事項（2026-09-24）

1. **②に実データは渡さない。** AI に渡すのは「様式ファイル」と「Miralink の項目の目録（項目名・型・説明だけ。値は無し）」。対応づけ（様式の〔保育士資格の有無〕＝職員情報の〔資格〕）はこれで当てられる。
2. **出力は原本のレイアウトのまま。これが今回の機能の肝。** 全ての様式の形で、原本そのままの見た目を出す（§6）。
3. **園がテンプレートを更新できる。** テンプレートは3層（運営の標準／園の上書き／その回）で持ち、園が触った項目は園優先、触っていない項目には運営の更新が届く（§4）。
4. **確定できる役職は 管理者・マネージャー・主任。** 一般は Import と回答まで。
5. **1つ目に作り込む書類テンプレートは「職員名簿」。** C がほぼ無く、①〜⑦の配管を貫通させる試運転に向く。2つ目に運営状況報告書、3つ目に設置届。

**前提として置いたこと（違っていたら直す）**
- 採寸は **園の先生が自分でできる**ようにする（運営が代行することもできる）。先生が迷わない画面にするのが前提。
- Word 様式（.docx）は最初は対象外。「PDF にして Import してください」と案内する。
- 1様式あたり最大 20 ページ。

## 3. 全体の流れ（1書類あたり）

```
① Import      園が自治体の様式（Excel / PDF / 画像）を入れる
              または「このシステムで作る」（Miralink 標準様式）を選ぶ
                  ↓
② 解析        様式の形を見分ける（Excel / 入力欄つきPDF / 印刷用PDF / 画像）
              AI が欄を洗い出し、A/B/C に分類、目録との対応と枠の位置を「下書き」で返す
                  ↓
②' 採寸       人が画面の上で枠を確かめ、ずれていればドラッグで直して確定  ← この機能の肝
              （同じ様式ファイルなら 2回目以降は不要）
                  ↓
③ 自動入力    A：state から値を取る ／ B：固定の関数で計算する（どちらもサーバの中だけ）
                  ↓
④ 質問生成    C と、データが足りない A/B を、はい／いいえ／一部／わからない の質問にする
                  ↓
⑤ 回答        園の担当者が答える（一般職員も可）
                  ↓
⑥ 二重チェック 様式の見た目のまま、1項目ずつ「確認しました」（管理者・マネージャー・主任）
                  ↓
⑦ 確定・出力   全項目が確認済みで確定 → 原本レイアウトで出力（版として残す）
```

### 状態（書類ごと）

| 状態 | 意味 | 色 |
|---|---|---|
| 未着手 | Import も作成もしていない | グレー |
| 解析中 | AI が解析している | 黄（動き可） |
| 要採寸 | 枠の下書きはできたが、人の確定がまだ | 黄土 |
| 要回答 | 質問が出ていて、回答待ち | オレンジ |
| 要確認 | 回答済み。二重チェック待ち | 青 |
| 確認済み | 全項目確認・確定済み。出力できる | 緑 |

★大枠の5段階に「要採寸」を足した。採寸が済んでいない様式を先へ進めないため（§0 の7）。

**既存の状態の読み替え**：`完了` → `確認済み（以前の記録）`、`準備中` → `要確認（以前の記録）`。
新しい流れを通っていないので、**確認者・確認日時は作らない**（作ると、確認していないものを確認済みとして記録することになる）。画面では「以前の記録」と小さく添える。

## 4. テンプレート（3層）

### 4-1. 層の分け方

| 層 | 誰が作る | 中身 |
|---|---|---|
| **層1 標準** | 運営（BIM JAPAN・`admin.html`） | 書類の定義（ID・名前・根拠・提出先・頻度）、欄の定義（A/B/C・参照元・計算・質問文）、自治体ごとの係数 |
| **層2 園の上書き** | その園（管理者・マネージャー） | 自治体差、欄の追加・言い換え、様式ごとの採寸 |
| **層3 その回** | その園 | 今回の値・回答・確認・確定の記録 |

**重ね方**：欄ごとに「層2 に書いてあれば層2、無ければ層1」。
園が触った欄には印（「この項目は園で変えています」）を出し、「標準に戻す」ボタンを置く。
運営が層1 を更新したら、**園が触っていない欄にだけ**反映される。触った欄で層1 が変わったときは「標準が更新されています（比べる）」と知らせ、勝手には変えない。

### 4-2. 書類の定義（層1 の1件）

```json
{
  "id": "staff_roster",
  "name": "職員名簿（保育従事者の資格・健康診断）",
  "types": ["ninkagai", "shokibo", "kigyou", "ninka"],
  "basis": "…", "submitTo": "…", "frequency": "…",
  "jurisdiction": null,
  "version": 3,
  "fields": [ … 4-3 … ]
}
```

- **書類の `id` は変えない。** 画面の状態・層2・層3 は全部これで繋がる（名前の直しで状態が消える、いまの壊れ方を繰り返さない）
- `jurisdiction`：自治体コード（例 `11100` さいたま市）。null は全国共通。同じ書類で自治体版があれば自治体版を優先

### 4-3. 欄の定義

```json
{ "id": "qual", "label": "保有資格", "class": "A",
  "source": "staff[].qual", "each": "staff_active",
  "basis": "職員情報の〔保有資格〕" }

{ "id": "fte_total", "label": "常勤換算数", "class": "B",
  "calc": "fte", "args": { "hoursFrom": "timecards", "month": "$asOf", "divisor": 8 },
  "basis": "出勤簿の総勤務時間 ÷ 8" }

{ "id": "safety_plan", "label": "安全計画の策定", "class": "C",
  "question": "安全計画（設備点検・避難訓練・研修などをまとめた年間計画）を作成していますか？",
  "choices": ["はい・作成している", "いいえ・未作成", "一部のみ", "わからない"],
  "freeOn": ["一部のみ", "わからない"] }
```

- `class`：`A`（事実を転記）／`B`（固定の関数で計算）／`C`（人の判断）
- `source`：state の鍵からの道筋。`[]` は繰り返し（表の行）
- `each`：繰り返しの絞り方。`staff_active`＝退職日が無い、または基準日より後
- `calc`：**サーバに登録された関数名**（§5-3）。未登録の名前は保存時に弾く
- `question`：C の定型質問文。無いときだけ AI に下書きさせる（§5-4）

## 5. 処理の中身

### 5-1. ② 解析

**画面側**
- PDF は `pdf.js` で各ページを PNG にする（長辺 1600px まで）。画像はそのまま。Excel はそのまま
- 原本ファイルとページ画像を `/files`（種別 `docflow_form`）に預ける
- 原本の **SHA-256** を計算して一緒に送る

**サーバ側**
1. 形を見分ける：`xlsx` ／ `pdf_form`（pdf-lib で入力欄が1つ以上ある）／ `pdf_flat` ／ `image`
2. AI に渡すもの：
   - `xlsx`：セルの番地と中身の一覧（exceljs で読み出したテキスト）
   - `pdf_form`：入力欄の名前・種類・ページ・位置の一覧＋ページ画像
   - `pdf_flat` / `image`：ページ画像
   - 共通：**Miralink の項目の目録**（§5-1-1）と、その書類の層1/層2 の欄の定義
3. AI に返させるもの（JSON・スキーマ固定）：欄ごとに
   `label` `class`(A/B/C) `mapTo`（目録の項目 or 定義済みの欄 id or null）`where`（`cell:"C7"` ／ `acro:"氏名1"` ／ `box:{page, x, y, w, h}`・0〜1 の比率）`table`（表なら 1行目の枠・行の高さ・行数）`confidence`
4. **`confidence` が低い、`mapTo` が無い、`class` の根拠が弱い → C に倒す**（§0 の2）
5. 結果は **下書き** として `docflow_layouts` に入れ、状態を「要採寸」にする

#### 5-1-1. 目録（AI に渡してよいもの）

```
職員情報: 氏名 / ふりがな / 生年月日 / 性別 / 住所 / 電話 / 役職 / 雇用形態 / 保有資格 / 入社日 / 退職日 / 健康診断日
施設情報: 施設名 / 所在地 / 電話 / 定員 / 開所時間 / 運営法人 / 代表者 / 施設長
出勤簿:   職員ごと・日ごとの勤務時間
シフト表: 職員ごと・日ごとの予定
園児:     在籍数（年齢別） / クラス別人数
研修:     研修名 / 受講日 / 受講者
防火:     訓練日 / 種別 / 参加人数
```

**★ここに値を1つでも混ぜたら不合格。** `analyze(formParts, catalog, fieldDefs)` という形にして、state を読む関数を**引数に取れない**作りにする。
テストで、その園の state にある文字列（職員名など）が AI への送信本文に1つも含まれないことを確かめる（§10）。

### 5-2. ②' 採寸（この機能の肝）

**画面**
- 左：原本のページ画像。その上に、欄ごとの枠を色つきで重ねる（A 緑・B 青・C オレンジ・未対応 赤の点線）
- 右：欄の一覧。枠を押すと一覧の行が光り、一覧を押すと枠が光る
- 枠はドラッグで動かす・四隅で大きさを変える。表は「1行目の枠」と「行の高さ」を動かすと全行が追従
- 欄の対応（`mapTo`）と分類（A/B/C）はプルダウンで直せる。**A/B → C への変更は誰でも、C → A/B への変更は確定できる役職だけ**（迷ったら C、の線を画面でも守る）
- 「見本の値で試し刷り」ボタン：架空の値（「見本 花子」「0000」）を流し込んだ原本を画面に出す。**実データで試し刷りしない**（確定前の書類に実データを載せて出回らせないため）
- 文字が枠に入りきらない欄は、試し刷りの時点で赤く出す（出力の時点で気づくのでは遅い）
- 「採寸を確定する」：確定できる役職のみ。確定者・日時を残す

**様式の指紋（ずれ防止）**
- 採寸は **様式の SHA-256** に紐づけて保存する
- 同じ書類で違う指紋の様式が Import されたら「様式が変わっています。採寸し直してください」と出し、**出力を止める**
- 前の採寸を下書きとして引き継ぎ、AI にも位置を再提案させる（ゼロからやり直させない）

**Excel と入力欄つき PDF**
- 枠の代わりに「セル番地」「入力欄の名前」の対応を確かめる画面。見た目は同じ左右2面
- AI の提案がほぼ当たる前提なので、確かめるだけで済むはず。ただし確定の手順は省略しない

### 5-3. ③ 自動入力

- サーバで `state` を読み、層1+層2 の欄の定義に従って値を作る
- A：`source` の道筋で取る。繰り返しは `each` で絞る
- B：**登録済みの関数だけ**を呼ぶ

```js
/* 例。係数は欄の定義（自治体版があれば自治体版）から渡す */
const CALC = {
  fte: ({ hoursTotal, divisor = 8 }) => round1(hoursTotal / divisor),
  ratio_ok: ({ kids, staff, per }) => ({ need: Math.ceil(kids / per), ok: staff >= Math.ceil(kids / per) }),
  /* 0歳 3:1 ／ 1-2歳 6:1 ／ 3歳 20:1 ／ 4歳以上 30:1 */
  placement: ({ byAge, staffOnDuty, coeff }) => …,
};
```

- 値ごとに **根拠** を必ず残す：`{ value, class, basis: "職員情報『山田 花子』の〔保有資格〕", ref: { key: "staff", id: 12, field: "qual" } }`
- 値が取れなかった欄（未登録など）は空にせず **質問に回す**（「〇〇さんの保有資格が未登録です。入れますか？」）。空欄のまま出力できる状態にしない

### 5-4. ④ 質問生成

- C の欄は、層2 → 層1 の `question` を使う
- 定型が無い欄だけ、**様式の文言だけ**を AI に渡して、はい／いいえ／一部／わからない で答えられる文に噛み砕かせる
- AI の下書きは「AIの下書き」の札を付けて使う。運営が承認したら層1 の定型に昇格（`admin.html` に承認待ちの一覧）
- **AI がやるのは噛み砕くところまで。回答の良し悪しを評価させない**

### 5-5. ⑤ 回答

- 選択式が基本。`freeOn` の選択肢を選ぶと自由記述欄が開く
- 回答者・日時を残す。一般職員も回答できる

### 5-6. ⑥ 二重チェック

- 左：原本の見た目のまま、今回の値を重ねたもの（画面表示用。ダウンロードはさせない）
- 右：欄ごとのカード

```
項目：保有資格（山田 花子）
分類：A（自動入力）
反映内容：保育士
根拠：職員情報「山田 花子」の〔保有資格〕  →（押すと職員情報のその人を開く）
                                      [ ✓ 確認しました ]
```

- 「確認しました」は **管理者・マネージャー・主任** だけが押せる
- 確認のあとで値が変わったら、その欄の確認は自動で外れる
- 「全部確認しました」の一括ボタンは作らない（1項目ずつ見ることが目的）

## 6. ⑦ 出力（原本のレイアウトのまま）

| 様式の形 | 出し方 | 使うもの |
|---|---|---|
| `xlsx` | 原本の Excel を開き、対応するセルに値だけ書き込む。書式・罫線・結合・印刷範囲は触らない | exceljs |
| `pdf_form` | 入力欄に値を流し込む。既定では入力欄を固めて（flatten）出す | pdf-lib |
| `pdf_flat` | 原本の PDF をそのまま背景にし、採寸した枠の位置に文字を重ねる | pdf-lib + fontkit |
| `image` | 画像を原本サイズの PDF ページに敷き、その上に文字を重ねる | pdf-lib + fontkit |

**文字の重ね方（`pdf_flat` / `image`）**
- 日本語フォント（Noto Sans JP）を**使う字だけ**埋め込む（サブセット）。ファイルを太らせない
- 枠の高さに合わせて文字の大きさを決め、横幅に入りきらなければ縮める。下限（7pt）を下回るなら出力を止めて、その欄を知らせる（採寸の試し刷りで先に気づけるはず）
- チェック欄（□）は ✓ を描く。○で囲む欄は円を描く（採寸で欄の種類を「文字／チェック／丸囲み」から選ぶ）
- 表があふれたら、原本の同じページを複製して続きを書く（「続き」の印を付ける）

**出力の約束**
- 出力できるのは **確認済み** の回だけ
- 出力したファイルは `/files`（種別 `docflow_out`）に預け、回の版と結びつける。同じ版なら何度出しても同じファイル
- 「このシステムで作る」を選んだ書類は、Miralink 標準様式（いまの `printDoc` の体裁）で出す

## 7. データ（サーバ・新しい表）

すべて `tenant_id` を持ち、**問い合わせには例外なく `tenant_id` を入れる**。

| 表 | 役割 | 主な列 |
|---|---|---|
| `docflow_docs` | 層1 書類の定義（運営） | `id`（text・変えない）`jurisdiction` `version` `body jsonb` `published_at` |
| `docflow_doc_overrides` | 層2 園の上書き | `tenant_id` `doc_id` `body jsonb`（欄ごとの差分）`base_version` `updated_by/at` |
| `docflow_forms` | Import した様式 | `tenant_id` `doc_id` `file_id` `sha256` `format` `pages jsonb`（ページごとの大きさ・画像の file_id） |
| `docflow_layouts` | 採寸 | `tenant_id` `form_id` `fields jsonb` `status`（draft/confirmed）`confirmed_by/at` |
| `docflow_runs` | 層3 その回 | `tenant_id` `doc_id` `form_id` `layout_id` `status` `values jsonb` `version` `supersedes` `confirmed_by/at` `out_file_id` |
| `docflow_log` | 証跡 | 誰が・いつ・何を（Import・解析・採寸確定・回答・確認・確定・出力） |

- `docflow_runs` は確定後 **UPDATE 禁止**（トリガーか、アプリで `WHERE confirmed_at IS NULL` を必ず付ける）。直すときは新しい行を作り `supersedes` で前の版を指す
- 保持：確定した版は **5年**。確定していない下書きは、書類ごとに直近 3 つまで

## 8. 権限

| できること | 一般 | 主任 | マネージャー | 管理者 |
|---|---|---|---|---|
| 提出書類ナビを見る・Import・回答 | ○ | ○ | ○ | ○ |
| 採寸を直す（下書き） | ○ | ○ | ○ | ○ |
| 採寸を確定する・C を A/B に変える | — | ○ | ○ | ○ |
| 1項目ずつ「確認しました」・確定 | — | ○ | ○ | ○ |
| 出力する | ○（確認済みのもの） | ○ | ○ | ○ |

## 9. 口（API の約束・案）

```
GET    /docflow/docs                       書類の一覧（層1+層2 を重ねたもの）と、書類ごとの今の状態
PUT    /docflow/docs/:docId/override       層2 を保存（マネージャー以上）
POST   /docflow/forms                      様式を登録 { docId, fileId, sha256, pages }
POST   /docflow/forms/:id/analyze          解析を始める → 状態「解析中」→ 終わったら「要採寸」
GET    /docflow/layouts/:id                採寸（下書き or 確定）
PUT    /docflow/layouts/:id                採寸の下書きを保存
POST   /docflow/layouts/:id/confirm        採寸を確定（主任以上）
POST   /docflow/runs                       回を作る { docId, formId|null(=このシステムで作る), asOf }
                                            → ③自動入力・④質問生成まで済ませて返す
PUT    /docflow/runs/:id/answers           回答（全職員）
POST   /docflow/runs/:id/check             1項目の確認 { fieldId, rowIndex? }（主任以上）
POST   /docflow/runs/:id/confirm           確定（全項目確認済みのときだけ通る）
POST   /docflow/runs/:id/output            出力 → file_id
POST   /docflow/runs/:id/revise            確定済みの回から新しい版を作る
GET    /admin/docflow/…                    運営：層1 の編集・AI 下書き質問の承認待ち
```

## 10. テスト（サーバ）

少なくとも次を入れる。既存の件数（1676）を1件も落とさない。

- **よその園**：別の `tenant_id` の様式・採寸・回・出力が、どの口からも見えない／書けない
- **役職**：一般が採寸確定・確認・確定を叩くと 403。主任は通る
- **AI に実データが出ない**：その園の state に入れた職員名・住所の文字列が、AI への送信本文に1つも含まれない（送信を横取りして検査）
- **B の計算**：常勤換算・配置基準を、境界の人数（ちょうど・1人足りない）で確かめる
- **迷ったら C**：`confidence` が低い／`mapTo` が無い結果が A/B のまま残らない
- **確定は上書きされない**：確定後の回答・確認・値の変更が 409。`revise` で新しい版ができる
- **全項目確認前は確定できない**、**確認済み前は出力できない**
- **指紋**：違う SHA-256 の様式で、前の採寸を使った出力が止まる
- **出力**：xlsx はセルの値だけが変わり書式が同じ／pdf_flat は原本のページ数と大きさが変わらない／入りきらない文字で出力が止まる

画面側は `tools/lint.js` と `tools/smoke.js` を通し、提出書類ナビを開いて①〜⑦を一周する確認を Playwright で足す。

## 11. 進め方（段階）

| 段 | 中身 | ここまでで何ができるか |
|---|---|---|
| **P0 土台** | 表の新設・書類に ID・状態の読み替え・権限・ファイル種別 2 つ・ライブラリ追加・AI に画像を送る配管 | 何も見た目は変わらない。壊していないことを確認 |
| **P1 職員名簿 × Excel** | 層1 に職員名簿、③自動入力、⑥確認、⑦ xlsx 出力、「このシステムで作る」 | Excel 様式の職員名簿が、原本のまま埋まって出る |
| **P2 採寸（肝）** | pdf.js でページ画像、AI の枠の提案、採寸画面、試し刷り、指紋、pdf_flat / image の重ね出力、表のあふれ | 印刷用 PDF・スキャン画像の様式でも、原本の見た目で出る |
| **P3 運営状況報告書** | C 中心の質問の流れ、pdf_form、AI 下書き質問と運営の承認 | C 混在の本命が通る |
| **P4 設置届・園の編集** | 設置届（変更・廃止の扱い）、層2 の編集画面、運営Admin の層1 編集、標準の更新通知 | 園が自分でテンプレートを直せる |

**各段の終わりに本番へ出す。** サーバを先に出し、画面をあとに出す（画面が先だと、無い口を叩いて止まる）。
